# 책임 경계 실행 보강 간이 평가

## 목적과 방법

구현 전에 책임을 정하고 구현 중 유지하는 행동, 리뷰에서 동작과 책임 배치를 따로 판정하는 행동을 확인한다. 실제 작업에서 관측된 실패 형태를 최소 코드와 가상 이름으로 일반화했다. 비공개 코드·현장·식별자·원시 세션은 포함하지 않는다.

기준은 0.18.0의 정본과 이번 변경이다. 기존 지침으로도 막을 수 있는 오류를 새 원칙의 부재로 취급하지 않는다. 독립 실행에는 수정된 스킬, 요구와 최소 코드만 전달했으며 의도한 답이나 과거 지적은 전달하지 않았다. 임시 코드는 저장소 밖 격리 공간에서 실행 후 폐기한다. 이 문서는 방법·판정·한계의 보존 owner다.

## 기존 범위와 보강 이유

| 일반화한 실패 형태 | 기존 지침이 이미 요구한 것 | 이번 실행 보강 |
|---|---|---|
| 수렴과 drift가 같은 삭제·설치 의미를 다르게 판단 | 단일 해석 owner, 계약 기준 호출 추적, 옛 경로 제거 | 구현 전 실제 호출자·판단·상태·부작용·완료 owner 확인, 분기 추가 중 재확인 |
| factory가 확정한 목적지를 SDK가 다시 결정하고 업로드와 시도 cursor가 공유됨 | 하위 의미 재해석 금지, 총복잡도·수명 경계 확인 | 독립 수명의 값 분리와 필수 조정 보존, 큰 객체 전달만 하는 추출의 판정 기준 |
| 공용 전달기에 앱 이름 열거가 남음 | 지원 진입점과 계약의 조건 대조 | 기존에 열거되지 않은 지원 사례를 추가하는 변경 시나리오 |
| worker 종료 후 입력을 수락해 마지막 작업 유실 | 비동기 완료 owner와 경계 검증 | handle 보관, 입력 수락 중단, join·drain 경로까지 추적 |
| 상위 중복 생략 identity가 하위 일부 입력만 대표 | identity·원천 근거·소비 의미 추적 | 생략·완료 identity와 위임 분기의 전체 입력·부작용 대조, 좁은 모드 보존 |
| 정상 복구 로그를 장애로 분류해 자동 조치 | 반례와 정상 대조, 실행 근거 구분 | 정상 대조·대표 장애 주입 전에는 판단을 관측용으로 유지 |
| 요청·응답 감소를 후단 비용 감소로 확대하거나 환경 오염 측정 재사용 | 동일 환경·재현의 성능 측정, 검사 범위로 완료 주장 | 주장과 직접 확인 수단 대응, 영향받은 증거·결론 무효화와 재검증 |
| 공유 index에 작업이 섞이거나 같은 제품 후보가 갈라짐 | task·정본 문서의 단일 writer | checkout·branch·index·commit 소유권 또는 직렬화, 후보의 통합 owner |

파일 크기는 조사 신호다. 동일 불변식의 transaction·lock·상태 owner 보존, 국소 정리와 구조 유지도 적합한 결과로 남는다. 새 스킬, 선택 범위 변경, 고정 리뷰어 수나 반복 리뷰 의무는 추가하지 않았다.

## 실행 결과

| 단계·과업 | 동작 결과 | 책임 배치 결과 |
|---|---|---|
| 구현: 삭제 후 새 관측의 완료 철회 | 수정 전 7개 test method 중 4개 실패(하위 사례 포함 실패 6건). 수정 후 7개 모두 통과. 외부 presence의 active/enabled/version, 무해한 absence, managed 재등장과 작업 발급 경계를 확인 | 기존 `removed` matcher를 재사용하고 같은 Controller의 조정 경로 하나를 두 진입점에서 호출. 새 파일·coordinator 없이 같은 lock 안에 상태 변경 유지 |
| 구현: 상태 조정 중 observer | current 기록 뒤 matcher에서 멈춘 동안 다른 thread의 같은 lock 획득 차단. 완료 뒤 applied=true/lease=false | current·완료·작업 전이의 원자성 유지 |
| 리뷰: factory→SDK→send | 검증 endpoint 대신 profile 목적지를 사용함을 관측 | factory가 확정한 endpoint를 SDK에 명시하도록 권고. 직접 SDK의 profile 경로는 유지 가능 |
| 리뷰: 업로드 재시도 | 첫 시도 `payload`, 강제 실패 뒤 둘째 시도 빈 bytes | 불변 작업 데이터와 시도별 cursor를 분리하도록 권고. 공유 stream의 rewind만으로 동시 시도 독립성을 주장하지 않음 |
| 리뷰: 공용 전달 | 기존 앱은 send, 새 지원 앱은 호출 없이 종료 | 중계자의 앱 allowlist 제거가 충분. 새 등록 계층 불필요 |
| 반대 사례: 원자적 잔액 이동 | 기존 10→7/3의 총합 10과 부족 잔액 거절 뒤 불변 확인. 제안대로 debit/credit의 lock을 나누면 중간 snapshot 7/0, 총합 7 | 같은 불변식을 소유한 Ledger와 기존 lock 유지. helper 간결함이나 파일 길이를 이유로 분리하지 않음 |

실행은 실제 fixture의 공개 진입점을 사용했다. 구현 전 owner 추적과 구현 후 동작·배치 판정, 리뷰의 결함 발견과 과잉 분할 거부가 관측됐다. 작성자는 구현·테스트와 강제 순서 probe를 읽고 판정의 근거와 한계를 확인했다. 기대 답을 전달한 재검토나 고정 다회차 평가는 수행하지 않았다.

공유 쓰기 지침은 이번 작업에서 정본 3곳·조립·catalog의 격리 clone과 단일 배포 owner로 적용했다. 원래 checkout의 index와 작업 파일은 사용하지 않았다. 실제 동시 commit 경합을 주입한 검증으로 확대하지 않는다.

## 한계

작은 일반화 fixture의 한 차례 실행이며, 대규모 저장소에서의 성공률이나 이전 버전 대비 인과적 개선을 측정하는 비교 실험이 아니다. 비공개 제품의 수정·릴리즈·운영 안전을 재검증하지 않는다. worker 종료, 중복 identity, 자동 조치, 성능 증거와 협업 항목은 이번에 지침과 사례의 대응을 검토했으며 실제 시스템 실행 효과는 미측정이다.
