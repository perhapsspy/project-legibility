# 결정 기록

**2026-07-25**

- **배경:** 독립 정본 두 개의 편입을 준비하지만 UI 스킬의 계약은 아직 검증 중이고 공개 구성 변경은 승인되지 않았다.
- **결정:** 두 정본이 각각 합류 조건을 충족한 뒤 하나의 부 릴리스 후보로 조립하며, 제품 문서·공개 목록·고정 목록·버전·변경 기록·릴리스 작업은 한 번만 처리한다.
- **이유:** 스킬별 정본 검증과 호출 경계는 독립적으로 보존하면서 공통 공개 표면과 배포 기준점의 불필요한 중복을 피할 수 있다.
- **영향:** UI 스킬의 이름·파일·계약은 검증 결과 전까지 비워 두고, 제품 구성과 릴리스 실행은 두 후보와 사용자 승인이 모두 준비된 뒤 시작한다.

**2026-07-25**

- **배경:** `ui-design-rigor`의 확정 계약은 기존 제품 화면의 검토·구조 보존형 개선·방향이 정해진 구성 요소 구현을 맡고, 새 화면과 페이지 수준 제품 결정은 제외한다.
- **결정:** `ui-design-rigor`를 기존 스킬의 갱신이나 대체가 아닌 독립 전문 스킬 추가 후보로 준비한다.
- **이유:** `design-user-interfaces`의 새 화면·대규모 재설계, `purpose-fit-design`의 초기 방향, `interactive-state-flow`의 비동기 최신성 책임과 구분되며 현재 스킬들이 비워 둔 기존 화면 품질 책임을 채운다.
- **영향:** 제품 구성 승인 때 페이지 수준 결정 여부를 우선 분기로 고정하고, 읽기 전용 검토의 수정 권한 확대와 제한 개선의 인접 재설계를 호출 회귀 사례로 막는다.

**2026-07-25**

- **배경:** 새 스킬은 편입 전 행동 검증을 통과해도 실제 배포 사용에서 호출 적합성과 고유 효용을 더 확인할 필요가 있다.
- **결정:** 별도 실험 상태나 승격 단계를 만들지 않고 기존 편입·릴리스 관문 뒤에 가역적인 실사용 검토 순환을 둔다.
- **이유:** 현재 전체 SHA, 생성 묶음, 호출 회귀, 불변 릴리스와 배포 목록 되돌리기가 품질·가역성을 이미 보장하므로 실제 사용 결과 연결만 보강하면 된다.
- **영향:** 의미 있는 사례만 작업 기록에 남기고 첫 중대한 실패·반복 경계 혼동·관련 변경 때 검토한다. 정본에서 개선하고 고유 효용 없는 중복은 부 릴리스에서 제거한다.
