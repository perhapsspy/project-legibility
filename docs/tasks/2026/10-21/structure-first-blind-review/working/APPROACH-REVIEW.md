# 리뷰 누락 개선 접근 재검토

2026-10-21, 사용자가 지엽적인 수정에서 벗어난 근본 재검토를 요청했다. 새 [Pro 상담](https://chatgpt.com/g/g-p-6a671998e7188191896c35aab9896689-codex-reasoner/c/6ad88c3c-88d8-83ee-956f-8c8ad7e1292f)에서 기존 권고를 전제로 삼지 않고 목표·평가·상담 운용을 검토했다. 이어 메인이 기존 실행 기록을 대조하고 그 직접 근거로 후속 상담을 마쳤다. Codex Reasoner 프로젝트 소속과 작성기의 Pro 설정을 확인했다.

**다음 개입은 공통 스킬 문구보다 넓은 리뷰의 작업 선택과 검증 비용 배분에 둔다.** 정본 `9b21db1`은 비교 기준으로 유지한다. 이번에 스킬·생성물·제품·릴리스를 수정하거나 새 worker 실험을 하지 않았다. 발견력 향상은 아직 입증하지 않았으며, 아래는 관측한 공백에 근거해 선택한 실행 방향이다.

## 기존 접근의 문제

메인이 누락 원인을 가르기 전에 상담 질문을 “스킬을 어떻게 최소 수정할까”로 좁혔다. Pro는 메인이 선정한 맥락과 평가 기준을 받았으며 직접 저장소·실행 기록을 관측한 독립 검증자는 아니었다. 문장이 타당하다는 판단을 행동 개선의 근거와 구분해야 했다.

singleflight 비교의 소스·계약·배정·재현 검사는 유효했다. 그러나 양쪽이 이미 성공한 111줄짜리 공개 사례를 반복해도 원래 여러 파일에 걸친 리뷰의 누락이 줄었는지는 판단하기 어렵다. 두 쌍은 같은 사례의 반복이며 마지막 문장 교체만 비교했다. 앞선 생성 근거 추적 문단 전체의 효과나 일반 스킬의 무효용도 이 결과로 판단할 수 없다.

A2는 외부 입력 이력의 도달성을 검증하지 않은 평가 기준이었다. 해당 실패 판정은 철회했다. A1과 다른 유효한 누락은 남아 있으며, 평가 정정을 리뷰 개선으로 세지 않는다. 알려진 결함의 재발 방지와 미지 결함의 발견력도 구분한다.

## A1 미발견·발견 기록 대조

미발견 기록은 0.17.1로 넓은 리뷰와 계약 지정 검토를 수행한 `01a15c21-43c8-7a33-8fcc-75436c169fd5`, 발견 기록은 새 NTP 집중 진단 `01a15c90-0375-7d03-8d6c-08be1d30e7b4`다. [구·신 비교](COMPARISON.md)와 [지정 진단](EVIDENCE-DIAGNOSTIC.md)이 원래 실행을 소유한다.

양쪽 실제 도구 반환에 NTP 새 수신 계약과 `ReadTimeHealthNTP`, `record.observeNTP`, `policy.Evaluate`의 완전한 함수 본문이 있었다. 필요한 파일명이 명령에 등장했다는 수준을 넘어, 함수 본문이 테스트 작성 전에 실제 출력됐음을 확인했다. 각 출력에서 줄 번호를 제거한 함수 본문은 각각 동일했다.

| 함수 | 줄 번호 제거 후 함수 본문 SHA-256 |
|---|---|
| ReadTimeHealthNTP | `9176daa1690c356105290851235f79d2e4ad8488cab97df5687efc8924ee23ac` |
| record.observeNTP | `449448eff1031e2d40f34d83d6e999acecc80433d8824786f4371d69daf90077` |
| policy.Evaluate | `0fb12711a5684dcb93444eaa87ce6f18e59314569d5ff2e85cdc3089b516c4b1` |

이 비교는 해당 함수의 노출·동일성을 확인한 것이며 전체 역사적 checkout과 환경의 동일성 검사는 아니다.

| 관측한 검증 | 미발견 실행 | 발견 실행 |
|---|---|---|
| 검증 시작점 | `FreshAcceptedID="new-1"`, baseline=`old`를 직접 구성 | 원시 패킷 메타데이터와 조회 성공·실패 이력 |
| 실행한 관계 | 파생된 NTP snapshot → policy의 독립 정상 관측·일정·reset | ReadTimeHealthNTP → observeNTP → Evaluate |
| 새 수신의 근거 | 테스트 입력으로 가정 | count=7·transmit·destination 고정, 최초 조회 실패 뒤 성공으로 바뀌어도 새 수신은 추가하지 않음 |
| 확인한 결과 | 공급한 snapshot에서 소비자 규칙은 정상 | 새 수신 없이 fresh=true·ntp_restored, 같은 패킷의 최초 가시성·실제 새 패킷 대조도 실행 |

미발견 실행의 소비자 테스트는 그 범위에서 유효했고 보고도 범위를 한정했다. 공백은 그 테스트가 새 수신이라는 계약상 사실을 직접 입증하지 않았다는 점이다. 같은 세션의 B는 불확실성 입력 → 실제 manual run → setter 호출의 검증·보고가 남아 있어 로그가 이런 실행 연결을 포착한다는 대조가 된다. B와 A1의 난도 비교로 사용하지 않는다.

따라서 세 함수·계약의 단순 미노출 설명은 약해지고, **노출된 생산자와 소비자 사이에서 필요한 사실을 검증하는 입력·이력이 선택되지 않았다는 실행 공백**으로 개입 위치를 좁힐 수 있다. 코드를 이해하지 못했다거나 특정 지침 때문에 경로를 배제했다는 인지적 원인은 확인하지 못했다. 입증한 A1을 보고에서 누락했다는 증거도 없다.

두 실행 사이에는 스킬 문구, 맡긴 계약 수, fresh 세션 여부와 기존 작업 문맥이 달랐다. 이 사후 대조는 문구 효과의 통제 실험이 아니다. 실행한 테스트의 차이로 다음 개입 위치를 선택하는 근거다.

## 다음 실제 넓은 리뷰의 실행 방향

작업 항목을 요청 범위의 주요 동작 계약으로 묶고, 각 검증이 무엇을 확인했으며 무엇을 입력으로 가정했는지에 따라 다음 작업을 고른다. 구조 설명과 동작 결함 검토의 성과를 구분한다. 중요 항목의 첫 경계 검증에 시간을 먼저 배분하고, 이후 영향도와 남은 불확실성에 따라 깊이를 늘린다. 모든 계약에 같은 깊이나 현장 실행을 요구하지 않으며 기존 작업 항목과 테스트를 사용한다.

A1이라면 소비자 reset 테스트를 더 늘리는 대신, 원시 패킷과 조회 이력에서 식별자를 만들고 최종 판정까지 연결하는 검증에 비용을 쓴다. 확정한 결함의 설명·중복 재현을 더 다듬는 동안 다른 중요 계약의 첫 검증이 밀리지 않게 한다. 동일한 경계·이력을 다룬 유효한 증거는 재사용한다.

핵심 전제를 직접 공급한 테스트만으로 해당 계약의 확인을 완료했다고 판단하지 않는다. 중요한 미검증은 보고서 말미의 단서로만 남기지 않고 남은 작업 순서를 바꾼다. 메인은 이미 승인된 범위의 필요한 검증을 이어간다. worker의 실험 상한과 사용자 전체 작업의 완료를 구분하며, 실제 범위·비용 결정이 필요한 경우에만 그 결정을 요청한다.

현재 일반 스킬은 책임과 증거 원칙을 맡고, 작업별 검토 범위·우선순위·비용 배분은 실제 리뷰 실행에서 정한다. 이미 확인한 제품 결함은 해당 제품 owner의 기존 회귀 근거로 방어한다. 이번 재검토에서 제품 테스트를 추가하거나 그 소유 저장소를 변경하지 않았다.

이 방식이 같은 예산에서 전체 누락을 줄인다는 것은 검증 전 가설이다. 다음 실제 넓은 리뷰에서 중요한 계약의 유효 발견, 확인한 경계, 남은 중요 공백과 비용을 함께 평가한다. 알려진 A1의 재발견이나 쉬운 공개 사례의 반복 성공을 새로운 발견력 향상으로 세지 않는다. 상설 평가 체계나 공통 다중 에이전트 절차를 추가하지 않는다.

## 상담 운용

앞으로의 상담은 먼저 어느 결정을 내려야 하는지와 경쟁 설명을 구분하고, 직접 관측과 해석을 나눠 전달한다. Pro의 답은 로컬 근거로 검증할 판단 자료로 사용한다. 이번에는 실제 기록을 대조해 단순 자료 미노출과 검증 연결 공백을 구분한 뒤 후속 판단을 받았다. 새로운 공통 문구는 실제 지침의 충돌·모호함이 필요한 검토를 방해했다는 근거가 있을 때 검토한다.
