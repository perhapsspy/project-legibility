## 후보와 판단 기준

같은 [Pro 상담](https://chatgpt.com/g/g-p-6a671998e7188191896c35aab9896689-codex-reasoner/c/6ad88c3c-88d8-83ee-956f-8c8ad7e1292f)에 실제 비교 피드백과 현재 스킬 원문을 전달했다. Pro는 중요한 작업의 편입과 자율 종료를 묶는 리뷰 전용 계약을 제안했다. 관련 소스 노출·잔여 예산은 확인됐지만, 누락의 내부 인지적 원인은 미확정이다.

첫 후보는 정본 `9b21db1` 위에서 다음을 바꾼다.

- 동작 리뷰는 작업 선택 전에 Verification을 읽고 종료 규칙을 적용한다.
- 범위의 명시적 공개 보장·진입점·출력과 실패 동작에서 작업을 도출하고, 같은 증거로 확인할 의무는 묶는다.
- 각 의무에서 실행 조건·의존성·상태 전이의 중요한 경계를 대표하는 검사를 선택한다.
- 심화·종료 전에 원래 범위와 실제 실행 증거를 대조한다. 실행 가능한 미검증 의무는 다음 작업이며, 미검증 표기만으로 제거하지 않는다.
- 대표 검사 확인 또는 명시적인 자원·접근·안전 한계에서 종료한다. 한계에 따른 종료는 미완료다. 모든 조합·현장 실행을 요구하지 않는다.

SKILL과 Verification의 한·영 네 파일만 수정했다. 일반 Runtime은 유지하고 Verification의 중복 첫 문장 하나를 제거했다. 후보는 독립 전이 정답을 열기 전에 고정했다. frontmatter 검사와 whitespace 검사는 통과했다. 아직 정본 commit/push·bundle 동기화·릴리스는 수행하지 않았다.

후보 1은 정상 current·만료, 제어 latch, JSON/protobuf current admission, 설치·pause·reinstall·resume, HTTP 거부, self-update snapshot/refresh/restore helper와 Linux cross-build까지 실행 범위를 넓혔다. 실제 Linux 실행·resident 재시작·owner I/O 오류·transaction rollback 전체는 실행하지 않았다. 후보는 미완료 이유를 12분 제한이라고 썼지만 실제 464.7초·24회 종료여서 약 255초·16회가 남았다. 내부 자원 사정은 미확정이며 명시 상한 소진으로 설명할 수 없다. 구 스킬은 원래 코드에 테스트 한 파일을 추가해 top-level 2개(하위 7개)를, 후보는 세 파일에 top-level 9개를 실행했다. 모두 현행 결함을 기대하는 특성화 assertion으로 같은 결과였다. 테스트 수 증가는 원래 발견 유지의 대체 근거가 아니다.

독립 전이는 개선 문구를 보지 않은 별도 담당자가 먼저 만든 합성 webhook delivery queue, 8개 Go 소스·546줄·전체 계약이다. 공개 입력과 비공개 witness·정상 대조·최소 수정본을 분리했다. 메인은 후보 고정 뒤 정답과 공개 API 도달성을 읽고 재실행했다. 원본 두 위반과 정상 대조, 최소 수정본의 동일 witness·정상 대조·race가 예상대로 나왔다. tenant/key의 허용 구분자 충돌, 만료 lease의 Ack/Retry 수락 두 결함은 원래 세 실패 구조를 그대로 옮긴 사례가 아니다.

전이 구 스킬은 상위 10개 검사 중 정상 8개·계약 위반 2개, 후보는 11개 중 정상 9개·계약 위반 2개였다. 공개 API로 만든 ID·token·deadline·상태를 사용했고 내부 정답 상태는 주입하지 않았다. 메인 race 재실행도 같았고 race 진단은 없었다. 양쪽 유효 발견은 같으며 후보의 추가 발견 이득은 확인되지 않았다. 합성 사례의 호환·관측 범위이며 일반 발견률이나 실제 외부 프로젝트 성능은 아니다.

## 두 번째 피드백 진행

첫 후보를 수용하지 않았다. A1을 놓쳤고 C의 독립 저장 정보 보존까지 연결하지 않았으며, 대표 검사가 있다는 사실이 전체 주장의 근거를 대신했다. 예산을 남긴 종료도 실제 상한과 맞지 않았다. 위 실제 테스트 코드와 실행 기록을 Pro에 다시 전달했다. 다음 수정은 작업 수를 더 늘리는 대신 대표 검사의 수용과 실제 남은 작업 선택을 연결하는 데 둔다. 원본 A1/B 유지·C 연결 경로라는 목표를 독립 전이의 성공으로 상쇄하지 않는다.

평가자 원본 witness는 새 복원 입력에서도 A1·B·C를 확인했다. C는 실제 coordinator 오류 생성·독립 저장→공개 status 연결이다. 이 자료는 리뷰어에게 전달하거나 발견 점수에 포함하지 않는다. 임시 코드·정답·원시 출력은 저장소 밖에서 유지하고, 최종 검토 후 정리한다.

## 후보 2와 세 번째 피드백

두 번째 Pro 답변에 따라 리뷰 절의 두 번째·세 번째 문단을 교체했다. SKILL 연결문·Runtime·첫 문단·일반 원천 추적 본문은 유지한다. 후보 2는 실제 시험 구성과 관측에 경계 증거 규칙을 적용한 뒤에만 해당 의무의 확인을 수용한다. 결론 주입·관련 증상만의 검사는 좁은 주장으로 제한하고, 별도 검사의 전달값·관련 이력이 연결된다는 근거가 없으면 빠진 관계를 다음 실행 가능한 검사로 남긴다. 종료 전 명시된 시간·호출 한도를 확인하고, 의미 있는 검사가 남으면 실행한다. 실제 한도 소진·관측한 장애 요인·원인 미상을 구분한다. 명시 예산이 없는 일반 작업에 새 예산을 요구하지 않도록 조건을 분명히 했다.

후보 2를 고정한 뒤 원본 입력에서 구 스킬 1명·동일 후보 2명의 fresh 실행을 미리 배정했다. 두 번째 후보 실행은 결과를 보기 전에 정한 재현성 확인이며 모든 결과를 보존한다. 새 `loop2_amber`, `loop2_violet`, `loop2_copper`는 중립 case에서 같은 과제·12분/40회로 실행했다. 보고서와 증거 고정 뒤 배정을 열었다. 추가로 기존 합성 사례의 사전 준비된 최소 수정본을 `loop2_teal`에게 정답·결함 수 없이 제공했다. 이는 후보 2의 정상 동작·오탐 대조이며 새 독립 발견 표본으로 세지 않는다. 새 발견이 나오면 기존 계약과 실제 근거로 판단한다.


| 실행 | 스킬 | 실제 발견과 검증 | exec / 경과 |
|---|---|---|---|
| amber | 후보 2 | A1의 실제 host parser→관측→정책, B의 parser→수동 경로. C는 owner I/O 미검증으로 남김 | 20 / 494.9초 |
| violet | 구 스킬 | A1의 host fact→관측→정책, B. C 미보고 | 25 / 453.4초 |
| copper | 후보 2 | B, 새 current의 backoff 우회, 관리 파일 손상→status=ok/health=nil. 독립 저장 owner 오류 보존은 확인하지 않음. A1의 생산자와 정책을 따로 검사했으나 복귀 판단으로 연결하지 않음 | 26 / 403.4초 |

후보 2 두 실행 모두 새 본문을 실제 도구 출력으로 읽었다. 명시 한도에 도달하지 않았다. copper는 자원 소진을 주장하지 않고 대표 경계 증거를 보고하는 범위 종료라고 명시했으나, 중요한 미검증 관계를 다음 실행으로 선택하지 않았다. 문구의 정확성과 필요한 실행 선택을 구분한다. 후보 2도 채택하지 않았다.

입력·동결 산출물은 모두 동일하게 유지됐다. 메인의 재실행은 amber 상위 5개·violet 4개·copper 7개 테스트가 같은 특성화 결과로 통과했고, 복사한 원본 구현도 입력과 같았다. 기록상 모델·effort·한도 및 금지 자료 조회 신호 부재를 확인했다. 통계 추출기가 중첩 또는 원문 stdout을 빠뜨려 생긴 스킬 미노출 표시를 원래 출력으로 재검사해 바로잡았다.

수정 합성 대조의 teal은 465.7초·12회였다. 알려진 두 수정과 정상 동작을 확인하고, `https://example.test/hook#`의 빈 fragment 수락을 새로 재현했다. fragment 금지라는 기존 계약에 비춰 유효한 별도 경계 결함이다. [RFC 3986 §3.5·§5.3](https://www.rfc-editor.org/rfc/rfc3986#section-3.5)도 구분자가 없는 상태와 내용이 비어 있는 상태를 구분한다. List의 잘못된 EndpointID 필터 수락도 재현했지만, 전역 ID 문법을 필터에 적용하는지 계약 해석이 남아 조건부 지적으로 분리했다. 메인 race 재실행은 정상 12개 통과·이 두 assertion 실패, race 진단 없음이었다. 최소 수정본은 알려진 두 결함만 고친 것으로 무결함 정답이 아니며, 새 발견을 오탐으로 강제 분류하지 않는다.

세 번째 Pro 피드백은 이 실행·실제 테스트와 종료 설명을 전달하고, 원칙 문장의 추가 대신 공개 보장→필요 원천 사실→실행 조건·실패 시에도 필요한 결과→실행 증거의 작업 절차를 재설계하도록 요청했다. 일반 최소 단위 원칙과 리뷰의 전체 범위를 구분하고, 기존 작업 계획의 짧은 범위·증거 대응표도 허용한다. 다음 후보도 무힌트 실행으로 검증하며, 기존 반복 기준선 증거는 재사용 여부를 명시한다. 영구 평가 체계·무조건 다중 리뷰·모든 조합·예산 확대는 추가하지 않는다.


## 후보 3: 보장별 실행·증거 대응 절차

세 번째 Pro 답변은 리뷰 절을 교체하고 일반 Runtime보다 앞에 리뷰 진입 규칙을 두도록 제안했다. 요청 범위가 검토할 보장을 정하고, 최소 단위·필요한 경로는 개별 검사의 크기를 제한한다. 일반 Runtime이 누락의 원인이었다는 인과 주장은 하지 않는다.

후보 3은 검사 선택 전에 모든 명시적 공개 보장을 계약 출처와 연결한다. 각각 필요한 사실·도달 가능한 조건이나 이력·관측할 assertion을 정하고 실패 시에도 유지되는 약속을 포함한다. 실행 증거는 정확히 검사한 assertion에만 연결하며 부분 증거가 남긴 항목에서 다음 검사를 선택한다. 종료 전에는 대응표를 원래 보장과 실행 증거 모두에 대조한다. 파일별 체크리스트·매 호출 일지·모든 입력 조합·일괄 운영 E2E를 만들지 않는다.

이번 쌍은 구 9b 기준선 반복 대신 후보 2 절차와 후보 3 절차를 비교한다. **양쪽 SKILL에 후보 3의 범위 진입 규칙을 동일하게 둔다.** Runtime과 일반 경계 증거도 같다. 따라서 두 Verification 리뷰 절만 다르며, 범위 우선권 명확화와 대응표 절차의 효과를 구분한다. 원본 source·전체 계약·보고 형식·새 Sol high·회당 12분/40회는 같고, 대응표 작성 비용도 포함한다. 103개 입력 해시를 고정하고 중립 배정 뒤 fresh `loop3_amber`와 `loop3_violet`를 시작했다. 정답·개수·위치·중간 피드백은 주지 않는다.

## 후보 4: 공개 assertion과 실제 호출 경계

네 번째 Pro 답변은 문구 구체화만으로 충분하다는 근거가 없으므로, 같은 worker의 번역·검사·갱신을 실제 호출 경계로 나누는 개입을 선택했다. 후보 4는 원문 조항의 정확한 문구·위치, 도달 가능한 조건·이력, 결과별로 독립 반증 가능한 공개 assertion을 기존 계획에 보존한다. 첫 검사 전 조항↔assertion을 양방향 대조하고, 준비를 공유하는 묶음마다 결과·근거·남은 검사를 갱신한다. 보장의 묶음이 아닌 검사 준비만 공유한다.

이번 한 쌍은 **같은 후보 4 자율 실행 ↔ 같은 후보 4 단계 재개 실행**이다. 103개 input 해시는 양쪽 모두 같다. source·전체 계약·모델·effort·fresh 조건·보고 형식도 같다. 단계군은 첫 호출에 번역·원문 대조까지만 수행하고, 같은 세션에서 열린 assertion/준비를 공유하는 묶음별로 재개한다. 초기 번역 최대 3분/10회를 포함해 최초 메시지부터 총 12분/40회가 계속 적용되며, 부모 대기·재개·갱신 비용도 포함한다.

배정·재개/갱신 누락/최종 대조 문구와 형식 판정 규칙을 실행 전에 고정했다. 부모는 단계군을 알아야 재개할 수 있으므로 이 실험의 운영자는 배정 맹검이 아니다. 대신 두 군이 끝나기 전 계획·보고·테스트의 의미 내용은 읽지 않고, 계획 파일 존재·hash 변화·REPORT 존재와 native 시간/호출만 확인한다. 결과를 보고 빠진 조항·검사 조건·정답을 재개 메시지에 넣지 않는다. 단계마다 계획 snapshot을 평가자 영역에 보존한다. REPORT가 처음 생기면 고정한 완료 대조 메시지 한 번을 보내며, 최종 반환 또는 실제 총한도에서 끝낸다. 형식·hash 확인은 의미 정확성을 보증하지 않는다.

무힌트 수용은 A1/B 유지+C 전체 관계의 직접 재현·보고다. 단계군만 성공하면 실행 운영의 잠정 근거이며 스킬 문구 단독 효과로 돌리지 않는다. 양쪽 성공은 단계 분할의 추가 이득 미확인이다. 충족한 고정 방식은 fresh 확인 한 번을 더 거쳐 반영한다. 실패 시 번역 소실·갱신/재개 불이행·검사 증거 부족을 분리해 계속 피드백한다. 아직 어느 후보도 채택·push·bundle 반영하지 않았다.

자율 amber는 507.5초·21회로 종료했다. 후보 4와 status guard·owner 오류 코드가 실제 출력에 나왔다. 단계 violet는 번역(118.4초/6회) 뒤 같은 세션을 네 번 더 재개했고, 매 검사 묶음에서 계획 hash가 바뀌었다. 부모는 해당 hash·존재·시간·호출만 읽고 고정한 재개 문구와 실제 남은 예산만 보냈다. 의미를 보고 빠진 항목을 알려주지 않았다. 계획은 실질 25조항에서 141개 assertion으로 늘어났다. B는 직접 확인했고 다른 정상·제어·갱신 검사를 추가했다. 정상·경계 범위 증가는 표적 발견 증가를 대신하지 않는다.

## 접근 자체에 대한 새 Pro 상담

질문을 기존 coverage 절차 보완에서 **결함 발견 리뷰와 계약 적합성 검사 사이의 작업 혼동**으로 바꿔 [독립 Pro 상담](https://chatgpt.com/g/g-p-6a671998e7188191896c35aab9896689-codex-reasoner/c/6ad8ec37-3670-83ee-b919-848c2294da74)을 시작했다. 정확한 Codex Reasoner 프로젝트·Pro 설정·저장 후 소속을 확인했다. 기존 조언도 비판 대상으로 삼도록 요청하고 모든 실패·조건·source의 실제 guard를 전달했다.

검토할 가설은 전체 약속을 정상 검사의 작업표로 바꾸는 방식이, 코드가 실제로 사용하는 조건·의존성·증거 전제를 계약과 비교해 반례를 찾는 탐색을 밀어냈을 가능성이다. 이는 내부 원인에 대한 확정 판정이 아니다. 기존 Runtime2에 있는 조건 비교를 실제 리뷰의 중심 작업으로 옮기고, 실행은 발견 후보의 증거를 만드는 데 집중하는 대안을 비판·설계하도록 요청했다. 세 알려진 결함 모양을 새 체크리스트로 넣거나 예산을 늘리지 않는다. 다음 후보와 실험은 답변을 실제 근거에 맞춰 판단한 뒤 고정한다.


## 후보 5: 코드 조건에서 반례를 구성

독립 Pro 답변은 후보 1~4의 누락 관리 개선을 발견 능력 개선처럼 다룬 조언을 수정했다. 적합성 검증 자체가 무용하다는 뜻은 아니다. 원본도 여유 예산에서 C를 놓쳤으므로 절차 비용 하나로 원인을 단정하지 않는다. 이번 개입은 기존 `9b21db1`의 Runtime2와 원천·이력 증거 규칙을 유지하고, 일반 범위 연결문과 모든 후보별 작업표·재개 규칙을 제거한 뒤 Runtime2 아래 리뷰 전용 문단 하나만 추가한다.

문단은 중요한 계약 동작의 실제 경로 조건을 바깥 guard·조기 종료·원천 사실까지 복원하고, 계약이 요구·허용·금지하는 결과와 대조한다. 계약상 같아야 하는 결과가 바뀌거나 구분돼야 하는 결과가 같아지는 도달 가능한 입력·상태·이력 변화를 구성해 예상 불일치를 밝힌다. 상위 불변식과 다른 경로로 가설을 반박한 뒤, 남은 전제·불일치를 관련 경계 검사로 확인한다. 국소 조사에서 그럴듯한 반례가 없으면 다른 중요한 동작으로 이동한다. 이 행동은 고정된 assertion 완주와 구분하며 별도 계획 형식을 요구하지 않는다.

## 후보 6: 결과 단위의 조건 비교와 다음 결과로 복귀

여섯 번째 Pro 답변은 후보 5의 반례 생성과 요청 범위를 유지하는 전환을 분리했다. 모든 경계를 먼저 훑어야 첫 재현을 시작할 수 있다는 전역 선행조건은 두지 않는다. 중요한 부작용·공개 결과와 그 성립 조건을 단위로 삼고, 반례 입증·반박 또는 국소 후보 없음 뒤 원래 범위의 아직 조건을 비교하지 않은 결과로 이동한다. 선택적 변형보다 이 전환을 우선하되 유효성·도달성 확인 대조는 유지한다. 읽기 전용 결과도 동등한 대상이다. 함수 출력이나 기능 이름만으로 조건 대조를 수행했다고 세지 않는다.

발견과 재현의 분리도 고정했다. ## 후보 6 결과: 다른 경계로 이동했어도 기존 발견은 유지되지 않음

동결 뒤 amber=후보 5·violet=후보 6이었다. 대조는 339.1초/21회에 B와 C를 발견·직접 확인했다. C는 정상 paused coordinator 시작 뒤 management를 손상시키고 실제 오류·횟수·기한 생성→저장→status 누락을 실행했다. 관리 의도만 복구하면 같은 record가 표시되는 대조도 있다. A1은 보고하지 않았다.

후보 6은 309.3초/20회에 B와 별도의 연결 복귀 의도 소실을 발견·재현했다. 원 Evaluate가 inspect 실패에서 backoff를 만들고, 같은 정상 current에서 복귀 시각만 backoff 안/기한으로 바꾸면 전자는 기한 뒤에도 ActionNone, 후자는 inspect_ntp가 된다. watcher의 한 번 callback과 coordinator flag 소비는 source로 연결했으며 이 전체 loop를 실행한 것은 아니다. 유효한 추가 발견으로 인정하지만 A1/C의 대체 점수로 쓰지 않는다.

후보는 B·정상 NTP 복귀 검사 뒤 연결 복귀 backoff의 반례로 이동했다. 따라서 발견 후 전환이 전혀 없었다고 해석하지 않는다. 다만 NTP 시험은 처음부터 유효한 accepted ID 기준선을 둔 정상 이력이라 초기 정보 부재·늦은 관측의 신선도 근거를 검증하지 않았다. status 전체 guard·owner 오류 코드가 실제 출력에 있었지만 독립 저장 기록의 표시 조건을 반례로 구성하지 않았다. 중요한 공개 결과 전체의 조건 비교를 확인하지 못한 채 약410초/20회를 남겼다.

메인 재실행은 대조 상위 2개, 후보 상위 3개 특성화 시험이 같은 결과로 통과했다. 입력·복사 구현·동결 산출물은 유지됐다. 같은 Sol high, 새 문구 실제 노출, 시간·호출 상한 이내, 금지 조회 신호 부재를 확인했다. 대조도 C를 찾았으므로 특정 새 표현의 효과를 주장하지 않는다. 후보 6은 채택하지 않았다.

일곱 번째 Pro 피드백에는 결과뿐 아니라 이 실제 검사 순서를 전달했다. 반례 생성·다른 경계 전환의 일부 이행과 전체 목표 실패를 구분하고, 짧은 문장 추가만으로 자기 완료 판단을 바꾸려는 접근의 한계를 다시 검토하도록 요청했다. 다음 개입은 아직 선정하지 않았다. 조항별 작업표·강제 재개·추가 예산·결함 모양의 힌트로 되돌리지 않으며 모든 실패와 다음 확인 실행을 보존한다.

## 후보 7: 상세 재현 전 경계별 조건·반례 비교

일곱 번째 Pro 제안에 따라 전환 지시를 더 강화하지 않고 비교 작업을 상세 재현에서 분리한다. 요청 범위의 부작용·공개 결과를 역추적해 생산자–소비자–약속된 결과 경계를 작은 임시 노트에 먼저 정한다. 같은 기능 이름으로 다른 결과를 합치지 않으며, 조항마다 행을 만들지도 않는다. 각 경계에서 원천 사실·이력으로 계약의 허용·의무를 먼저 쓰고, 별도로 실제 guard·근거 변환·결과를 도출한다. 코드가 금지된 결과를 만들거나 필수 결과를 누락하는 구체적 입력·상태·이력을 대입하고, 도달성·예상 불일치 또는 시도를 막는 소스 불변식을 남긴다. 허용을 의무로 뒤집지 않는다.

상세 발견을 다듬기 전에 이 순회를 수행하되 작은 전제 probe는 허용한다. 이후 기존 Verification으로 유망한 반례와 미해결 전제를 집중 확인한다. 정상 성공·소스 출력·일반 확언·발견 수를 경계 비교의 대체 근거로 쓰지 않는다. 모든 경계의 시험이나 완전한 계약 모델을 요구하지 않는다. 후보 6의 Runtime 경로 문장과 9b Verification은 유지하고 리뷰 세 문단만 교체했다. 한·영 의미·형식·whitespace 검사와 7파일 동결을 완료했다.

**후보 6 ↔ 후보 7 본실행·확인 두 쌍**을 첫 실행 전에 함께 고정했다. 네 실행 모두 같은 새 Sol high·전체 입력103개·TASK·자율 실행·각12분/40회이며 노트 비용도 포함한다. 두 SKILL만 다르고 정답·개수·위치·과거 결과·중간 개입은 없다. 첫 쌍의 성공 여부와 무관하게 네 결과 모두 수행·보존하고 고정 후 배정을 연다. 수용은 두 처리 실행 모두 실제 구체적 패스와 A1/B/C 발견·관계 재현을 충족하는 것이다. C reader witness와 coordinator 생성 범위를 분리하며 새로운 전체 E2E 조건을 두지 않는다.

실패 해석도 고정했다. 중요한 결과가 목록에서 빠지면 구조 기반 선택이 부족하다. 일반 문구·정상 성공뿐이거나 여유 예산에서 중요한 후보를 남기고 종료하면 절차가 기대 작업을 유도하지 못한 것이다. 실제 부정 조건·도달성 비교를 했어도 놓치면 한 차례 패스의 탐색 충분성이 지지되지 않는다. 준비만으로 예산을 소진하면 이 예산에 부적합하다. 성공해도 알려진 사례의 국소 개선이며 일반 발견률·통계적 안정성을 주장하지 않는다.

## 후보 7 결과: 조건의 의미 보존과 닫힘 판단이 부분 이행

두 쌍 모두 amber=후보 7·violet=후보 6이었다. 네 산출물 전체를 먼저 고정하고 배정을 열었다. 같은 Sol high·문구 실제 노출·시간/호출 상한 이내·금지 조회 신호 부재를 확인했다. 메인이 추가 코드를 검토한 뒤 전체 시험을 재실행했고 네 실행 모두 자체 상위4개 특성화 PASS였다. 입력·복사 구현·동결 산출물은 재실행 후에도 유지됐다.

| 실행 | 스킬 | 발견과 실제 관계 확인 | 실제 시간/exec |
|---|---|---|---|
| 본 amber | 후보 7 | A1·B 발견, 원 parser→수신 변환→정책과 Date→run 실행. C는 record 없는 손상 관리 의도의 status 증상만 | 445.7초/18회 |

본 후보의 A1은 같은 과거 packet과 첫 metadata 가시성 대조로 허위 복귀를 확인했다. fixture host 원문과 시간·관측을 직접 넣어 원 host parser→observeNTP→Evaluate를 실행했으며 실제 resident의 조회 admission·타이머를 실행한 시험은 아니다. B는 모두 원 Date parser가 구간을 만든 뒤 manual/automatic을 대조했다. fallback backoff는 원 Evaluate가 만든 실패 수·NextAttempt/NextNTPCheck 이력에서 세 번째 실패의 30분 대기보다 25분 먼저 inspect_ntp가 나오는 것을 확인했다. host 실패·실제 대기까지 실행한 것은 아니다. 새로운 결함은 세 기존 표적의 부족분을 상쇄하지 않는다.

두 후보는 상세 시험 전에 8개 안팎 경계 노트를 만들었고 일부 구체적 반례·소스 불변식 대입을 수행했다. 준비 비용이 예산을 소진하거나 패스가 전혀 실행되지 않은 경우는 아니다. 그러나 본 후보는 owner 재시작/status를 같은 넓은 행에 묶어 boot·기한 보존만 쓰고 오류·횟수·retry 공개의 독립 조건을 누락했다. record 없는 status 증상을 확인한 뒤 그 경계를 닫았다. 확인 후보는 계약의 ‘회복 구간에 새로 받은 정상 응답’을 구현의 ‘새 accepted ID’로 바꾸고 FreshNTPSeen을 직접 넣은 소비자 시험으로 비교했다. 원천 수신 사실의 정당화는 미실행으로 남긴 채 종료했다. 전체 구체적 부정 조건 패스가 충족됐다고 볼 수 없다.

후보 7을 채택하지 않았다. 약274~314초와 20회 이상 남은 처리 실행의 종료는 한도 소진이 아니다. 관측한 실패 단계는 경계·계약 의미 선택과 조건 비교의 부분 이행이며, 실제 노트가 있다는 사실은 이를 보증하지 않는다.

여덟 번째 Pro 피드백에는 실제 노트 원문·도구 순서·네 결과를 전달했다. 구현을 본 뒤 계약 조건을 재서술해 구현 표현을 상속했을 가능성을 새 가설로 다룬다. 계약 원천 의미를 코드 열람 전에 짧게 고정하는 방식과, 같은 총예산 안에서 새 맥락이 근거·누락을 비판하는 실행 기제를 비교 판단하도록 요청했다. 이는 원인 확정이나 새 방식의 채택이 아니다. 후보 8 문구를 자동 추가하지 않고 답변과 실제 실패 단계로 다음 개입을 정한다.

## 실행 기제 8: 같은 첫 리뷰를 기존·새 맥락이 재심사

Pro8은 노트 작성 순서 잠금과 새 문구를 함께 추가하지 않고, 첫 리뷰의 근거·완료 판단을 비판하는 실제 인계를 선택했다. 첫 단계는 고정 후보 7로 최대360초/20회 또는 자율 종료까지 수행한다. 실제 존재하는 전체 산출물을 고정·복제해 두 후속 실행의 같은 출발점으로 쓴다. 한쪽은 같은 worker/맥락, 다른 쪽은 새 Sol high/fork none이다. 두 쪽에 같은 원자료와 초안·노트·시험을 제공하고 같은 비판 과제를 준다. 부모는 요약·빠진 의무·우선순위를 덧붙이지 않는다.

비판 과제는 원 요청·전체 계약·소스를 기준으로 중요한 누락 의무나 근거 없는 검토 완료 주장을 고른다. 원 계약 사실→현재 코드·시험이 실제 보인 사실→빠진 추론→확인 결과만 작은 노트에 남기며 원천 생산·소비 경로의 구체 반례를 확인한다. 기존 유효 재현은 재사용하고 원천 의무와 관련 사례·구현 label을 구분한다. 결합 보고가 평가 단위이며 첫 단계·후속 발견/실행 범위도 보존한다. 부모가 유리한 발견만 사후 합치는 방식이 아니다.

본·확인 각각 별도 공통 첫 리뷰를 시작하는 두 비교를 사전 고정했다. 각 arm은 공통 첫 단계 비용을 전부 부담하고, 복제·전달·대기·후속까지 최초 시작 기준 총720초/40회 안에서 실행한다. 공통 비용을 반으로 나누거나 후속에 새 전체 예산을 주지 않는다. 같은 절대 마감과 첫 단계 후 남은 명령 상한을 적용한다. 첫 결과가 이미 성공해도 버리지 않는다. 공통 초안을 공유하므로 네 독립 자율 리뷰로 표현하지 않는다.

운영자는 같은 맥락의 worker를 재개해야 하므로 배정을 알지만, 인계 때 산출물 의미를 읽거나 새 피드백을 쓰지 않는다. 형식·존재·hash·native 시간/호출만 감시하며 결과 고정 후 판정한다. 두 fresh 결합 결과 모두 기존 목표를 충족해야 국소 수용한다. 양쪽 모두 충족하면 새 맥락의 필요성을 주장하지 않고 더 작은 같은 맥락 비판 방식을 우선한다. 정본 스킬은 후보 7로 고정했으며 아직 영구 다중 에이전트 규칙이나 후보 8 문구를 게시하지 않았다.

## 실행 기제 8 결과: 같은 맥락에서도 기존 세 관계를 확인

네 결합 보고 모두 A1/B/C를 발견·관계 재현했다. 공통 첫 리뷰는 본·확인 각각 A1을 놓쳤고 B와 유효한 저장 record를 둔 C reader 관계를 확인했다. 후속 비판은 원 계약의 실제 새 수신과 기존 accepted-ID 소비 guard 사이의 미입증 연결을 다시 열어, 고정 packet/관측 가시성의 반례를 만들었다. 본·확인 두 쌍 모두 같은 맥락에서도 이 행동이 나왔으므로 새 worker가 필요하다는 근거는 없다.

| 비교·후속 | 최초 시작→결합 종료 | 첫 단계·인계 포함 exec | 기존 세 관계 | native 세션 |
|---|---:|---:|---|---|
| 본·같은 맥락 | 662.5초 | 29 | A1/B/C 확인 | `01a15fa4-625e-7140-8de8-160f27328223` |
| 본·새 맥락 | 592.0초 | 31 | A1/B/C 확인 | `01a15fa8-cfd6-77f0-8b51-e68484f3c0cc` |
| 확인·같은 맥락 | 698.0초 | 31 | A1/B/C 확인 | `01a15fa4-7c24-7ec2-b4cd-e3691b3e2485` |

각 arm은 본 첫14회·확인 첫17회 비용을 전부 부담하고 인계 복제1회도 더했다. 전달·대기·후속을 포함해 모두 최초 시작 기준720초/40회 안이며 마감 뒤 shell 실행은 없다. 같은 Sol high, 허용한 clock/exec/poll 외 도구 없음, 금지 조회 신호 부재를 확인했다. 원자료·복사 구현·고정 공통 산출물과 최종 산출물 hash는 유지됐다. 기록 검증이며 OS 접근 격리는 아니다. 같은 상한이지 실제 토큰 소모를 맞춘 실험은 아니다.

실행 범위는 다음과 같다.

- A1: 본 같은 맥락은 host 원문→ReadTimeHealthNTP→observeNTP→예약·완료 Evaluate를 실행했다. 본 새 맥락은 원 NTPMessage parser→observeNTP→Evaluate의 지역 관계를 실행했으며 resident admission 전체는 실행하지 않았다. 확인 새 맥락은 1·6·11분의 매 inspect action을 먼저 확인하고 원 host reader부터 연결해 초기 metadata 실패·기존 packet 대조·실제 새 packet 대조를 실행했다. 확인 같은 맥락은 실제 packet 수신290초·새 실패 경계600초를 고정하고300초 조회 가시성만 바꾼 별도 지원 이력이다. 원 A1과 같은 근거 결함 계열이며 구체 이력 차이를 보존한다.
- B: 공통 첫 단계의 원 Date parser→manual run과 자동 거절 증거를 재사용했다. 본 fixture는 같은 관측 값을 두 호출에 공급했으며 실제 독립 TLS 수신을 실행하지 않았다. 확인 같은 맥락은 순차 finished/Date를2초씩 진행시킨 두 표본으로 추가 보강했다. 기존의 별도 fresh 표본 witness와 같은 공통 안전 guard 위반이며 전체 TLS·clock syscall 증거로 넓히지 않는다.
- C: 두 공통 첫 단계가 실제 파일에 유효한 owner 오류·횟수·retry record를 두고 management 오류가 public status에서 이를 가리는 reader 관계를 실행했다. coordinator가 만든 record라는 주장은 하지 않았다. 본 같은 맥락은 정상 paused owner→관리 오류→실제 count·retry 저장→status 소실까지 추가 실행했다. 이 추가 범위는 다른 reader witness의 새 필수조건이 아니다.

### 후보 12: 원계약의 소비 결과 목록이 첫 조사 순서를 결정
