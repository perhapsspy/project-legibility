# 같은 스킬에서 리뷰 수행 방식 비교

2026-10-21, 당시 여러 파일에 걸친 Edge 시간 동기화·resident 복원 fixture로 새 worker 한 쌍을 실행했다. **기존 방식과 제안 방식 모두 유효한 기존 세 결함 중 A1·B 두 건을 무힌트로 발견했고 C는 놓쳤다. 이번 한 쌍에서 제안 방식의 추가 발견 효과는 확인하지 못했다.** 스킬·제품·생성 bundle·릴리스는 변경하지 않았다.

## 고정 조건과 개입

| 항목 | 양쪽 공통 조건 |
|---|---|
| 입력 | 같은 소스·전체 제품 계약 48줄·현재 스킬, 103개 파일 |
| 스킬 | 정본 `structure-first`의 `9b21db1efe765c3ccf08c75f5627c4c8f8850309`, 7개 파일 동일 |
| 실행 | 새 `gpt-6.1-sol/high` worker 각각 한 명, `fork_turns=none`, 자식 위임 없음 |
| 예산 | 시작부터 최대 12분, `exec_command` 최대 40회, 각 1회 |
| 공통 과제 | 구현의 문제점·과도한 책임과 얽힘 검토. 필요하면 자체 테스트·복사본 실행. 발견과 실제 검증 범위를 따로 보고 |
| 비공개 | 정답·결함 수·위치·과거 결과·평가자 재현·부모 대화·다른 case·세션·메모리 |
| 종료 | 무힌트 단계만 수행. 누락 조항 지정·후속 힌트·결과를 바꾸기 위한 재실행 없음 |

기존 방식은 구조·호출·상태·부작용을 파악하고 위험한 부분의 조사 순서와 예산을 자유롭게 정하는 일반 리뷰다. 제안 방식은 같은 지시에 다음 수행 규칙만 더했다. 초기 구조 파악 뒤 주요 도메인 계약을 작업 단위로 삼고, 한 발견을 심화하기 전에 중요한 계약의 미입증 전제에 첫 경계 검증 시간을 배분하며, 실제 확인과 가정을 구분해 영향·남은 불확실성으로 다음 검증을 선택한다. 특정 계약·입력·파일 예시는 주지 않았다. 과거 모든 내부 판단을 그대로 재생한 대조는 아니며, 일반 리뷰와 이 추가 지시의 비교다.

배정은 중립 case 이름에 무작위로 고정했다. 프로토콜·채점 기준을 먼저 저장하고, 양쪽 보고서·테스트·증거 해시를 고정한 뒤 배정을 열었다. `case-slate`가 기존 방식, `case-jade`가 제안 방식이었다. 파일·함수 수를 의미상 검증 범위 점수로 쓰지 않았다. A2는 외부 이력 도달성 미확인으로 평가에서 제외한다.

예산은 같은 시간·도구 호출 상한이다. 실제 소비 토큰·요금이 같은 금액이 되도록 통제한 실험은 아니다. 양쪽 모두 상한 전에 자율 종료했다.

## 발견 결과

| 사전 고정한 유효 결함 | 기존 방식 | 제안 방식 |
|---|---|---|
| A1: 최초 메타데이터 조회 실패 뒤 과거 NTP 패킷을 새 수신으로 오인 | 발견·실행 재현 | 발견·실행 재현 |
| B: 수동 `run`이 전체 불확실성 구간 안전조건을 우회 | 발견·실행 재현 | 발견·실행 재현 |
| C: management 오류가 독립 저장된 owner 오류·횟수·재시도를 status에서 숨김 | 미보고·해당 조합 미실행 | 미보고·해당 조합 미실행 |
| 합계 | 2/3 | 2/3 |

추가 발견은 표적 점수에 합산하지 않았다. 기존 방식은 세 번째 NTP 조회 실패 후 `NextAttempt=45분`인데 20분에 다시 조회하는 backoff 우회를 정책 전이로 재현했다. 제안 방식은 IMF-fixdate 계약에 없는 소수 초 Date가 parser에 수용되는 현상을 관측했다. 후자는 문자열→관측 helper의 실제 반환을 로그로 확인한 결과이며, 테스트 자체에 acceptance assertion은 없다. 실제 clock 위험으로 확대하지 않는다. 두 추가 관측은 각각 제공 계약과 코드·재실행에 부합했다.

## 실제로 검증한 경계

| 경계 | 기존 방식 | 제안 방식 |
|---|---|---|
| HTTP 관측→수동 clock 쓰기 | 실제 응답 parser가 만든 `5.5초±1.1초`를 run에 연결, setter 1회. 같은 입력의 automatic run은 0회 | 실제 header parser가 만든 `6초±3초`, `24시간±3초`를 run에 연결, 각각 setter 1회. 안전한 `10초±3초` 대조와 automatic 판정 helper도 실행 |
| NTP 패킷→신선도→복귀 | 실제 NTPMessage parser→`observeNTP`→`Evaluate`. 고정 패킷·조회 실패/성공·AP 해소를 입력. 기존 패킷이 처음부터 보이는 대조는 fallback, 새 count는 복귀 | 같은 세 함수 연결. 고정 패킷·조회 실패/성공·restart 실패·idle readback을 입력. 정책이 정한 대기·재조회 뒤 복귀. 처음부터 보이는 고정 패킷·새 count 대조 실행 |
| NTP 실패 스케줄 | 영 상태에서 fallback 진입→조회 3회 실패→30분 기한 전 5분 조회 발행 | control 성공 후 `ControlIdle=false`를 주면 latch 유지·60초 후 조회 예약. worker 30분 backoff 우회는 시험하지 않음 |
| 정상 current 비용 | source 흐름 추적, 해당 무작업 계약 테스트 없음 | fresh 정상 observation→policy에서 추가 action 없음·7분 만료 기한 실행 |
| Date 형식 | 정상 IMF Date를 다른 테스트의 입력으로 사용 | 정상·잘못된 일자·소수 초 문자열의 실제 parser 반환 로그 관측 |
| owner I/O 오류→저장→공개 status | source 읽기, 해당 경계 실행 없음 | source 읽기, 해당 경계 실행 없음 |
| install/pause/remove·self-update·Linux 알림 | 읽기·부분 callsite 추적, 실제 lifecycle 미실행 | 읽기·부분 callsite 추적, 실제 lifecycle 미실행 |

양쪽의 offset·uncertainty·accepted ID·정책 상태/기한은 실제 원본 함수가 만들었다. HTTP 응답·시각·RTT·busctl 문자열·unit 사실·메타데이터 실패·시간 observation·worker 결과는 worker가 만든 fixture다. **두 NTP 테스트 모두 전체 `ReadTimeHealthNTP`의 외부 명령 호출은 실행하지 않고, parser 이후의 연결을 실행했다.** 수신 속성 그룹 실패를 표현하는 플래그는 직접 입력했다. 따라서 전체 resident·실제 D-Bus·서비스·네트워크에서 얻은 결과로 세지 않는다. 내부 fresh flag나 baseline을 정답 상태로 넣은 소비자 단독 테스트와는 구분된다.

C에 관해서는 두 세션의 실제 도구 반환에 `timeSyncStatus` 전체와 coordinator owner 오류 처리 본문이 포함됐음을 확인했다. 파일명만 검색한 경우가 아니다. 그러나 management 오류를 유발하고 독립 health 저장 결과를 status로 읽는 조합은 선택하지 않았다. 소스 노출만으로 검증 완료를 인정하지 않으며, 미보고의 인지적 원인은 이 기록으로 판정하지 않는다.

## 재실행과 통제 확인

메인은 양쪽이 만든 테스트를 원본과 동일한 구현 복사본에서 `go test ./cmd/edge-agent -run '^TestReview' -count=1 -v`로 재실행했다. 기존 방식의 top-level 4개, 제안 방식의 5개가 같은 관측으로 끝났다. 제안 방식의 Date 항목은 assertion 없는 로그 관측이므로 5 PASS를 다섯 계약 검증 성공으로 세지 않는다. 모든 원본 구현 파일이 입력과 동일했고, 각 복사본에는 테스트 파일 하나만 추가돼 있었다.

양쪽 worker의 `go test ./...`도 제공 package에서 성공했다. 원래 테스트를 모두 제외한 fixture이므로 이는 추가 테스트와 빌드 확인이며 전체 과거 회귀 검증이 아니다. 메인은 별도 비공개 대조에서 실제 `ReadTimeHealthNTP`→변환→정책의 A1, 수동 명령 B, 실제 coordinator 오류 생성·저장→status의 C가 여전히 관측됨도 확인했다. 이 대조는 채점 기준 고정 뒤 worker와 독립적으로 수행했고, 발견 점수에 포함하거나 worker에 전달하지 않았다.

| 실행 기록 | 기존 방식 | 제안 방식 |
|---|---:|---:|
| `exec_command` 호출 | 15 | 17 |
| 시작→완료 | 약 440초 | 약 428초 |
| 한도 준수 | 확인 | 확인 |
| 세션 | `01a15edf-e096-7541-9629-78ef6552e215` | `01a15edf-c493-7fc0-ab5e-8433ebbc522d` |

모델·effort·스킬과 두 reference 읽기를 실행 기록에서 확인했다. 다른 case·평가자·원본 checkout·세션·메모리 조회 신호는 기록된 명령에 없었다. 이는 지시·도구 기록 검사이며 OS 접근 격리는 아니다. 보고서 고정 뒤에도 입력 103개와 보고서·테스트·증거 해시가 유지됐다. 공통 입력 manifest의 SHA-256은 `2bc7875bcd40752d3f61b52bb43162342c3ba4459f1b69e40c9c9629d30f6562`다.

핵심 세 구현은 [원래 복원 범위](RESULTS.md)의 역사적 해시와 일치하고 Host 파일도 당시 출력과 같다. 나머지 소스는 후속 지원 snapshot이므로 전체 과거 checkout을 복원했다는 주장은 하지 않는다. 실행 환경은 Go 1.27.2 darwin/arm64, module Go 1.25.0이다. 실제 Linux·설치 binary·현장 동작은 시험하지 않았다. 임시 소스·테스트·원시 출력은 검토 뒤 정리하고, 이 요약과 원래 Codex 실행 기록을 보존한다.

## 판정

이번 비교에서 **제안한 예산 배분 지시의 추가 효과는 미입증**이다. 기존 방식도 A1의 생산자 일부→소비자 연결을 선택했고, 제안 방식도 C의 경계에는 실행 시간을 배분하지 않았다. 두 실행 모두 약 7분에 종료해 같은 12분 상한을 남겼으므로 시간 고갈로 설명할 근거도 없다.

이는 현재 스킬을 고정한 한 쌍의 수행 방식 비교다. 이전 0.17.1의 미발견 결과와 비교하면 입력 스킬·fresh 실행 등이 달라지므로, 이번 A1 발견을 새 수행 규칙이나 스킬 문구 하나의 효과로 귀속하지 않는다. 일반 발견률, 일반 스킬의 무효용, 어느 방식의 우열도 이 표본으로 판정하지 않는다. 현재 스킬을 유지하며 이번 요청의 비교는 종료한다.
