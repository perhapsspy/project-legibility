# Skill: Source Owner Audit

## 목적과 범위

현재 소스 근거로 답한다.

- 무엇을 따라야 하는가?
- 무엇이 다른가?
- 무엇이 아직 결정이 필요한가?

기본 범위는 읽기 전용 근거 확인, 비교, 분류, 소유권 수준의 권고다. 조사만, 금지, 제외, 범위 제한 표현은 실행 경계로 고정한다. owner 근거는 책임을 밝힐 뿐 수정, 정리, 구현 순서 또는 사용자 승인 범위 밖의 실행을 허가하지 않는다.

## 근거 규칙

각 후보 owner를 가장 작은 현재 소스 경로에서 독립적으로 확인한다. 사용자가 지목한 기능, 경로, API, 설정, 문서, 동작에서 시작하고 넓은 검색보다 경로별 읽기를 우선한다. 로컬 변경이 답에 영향을 줄 수 있으면 작업트리 상태와 관련 diff를 확인한다.

현재 소스는 메모리, 이전 요약, 과거 작업 노트, 오래된 문서, 후보 구현보다 우선한다. 현재 owner를 확인하기 전의 결론은 추론 또는 현재 근거 부족으로 표시한다. 근거가 부족하면 개연성으로 owner나 제품 값을 선택하지 말고 빠진 결정을 보고한다. 확인된 사실과 추론을 분리한다.

질문에 필요한 소유 경로만 따라간다. 호출자, 어댑터/클라이언트, 경로/API, 명령/서비스, 저장소/스키마, 테스트, 설정, 런북, owner 문서가 해당할 수 있다. 현재 운영 owner와 파생/라우터, 레거시/호환, 오래됨/대체됨, 생성물/복사본, 근거 전용 표면을 구분한다.

질문이 여러 경계를 가로지르면 소스/계약, 호출자/UX, 쓰기/읽기, 문서/작업, 이관, 결정 owner를 구분한다.

기능 존재만으로 호출자 의도, 접근 정책, 제품 승인, 화면 동작 일치를 증명할 수 없다. 각각 별도 근거가 필요하다. 현재 owner 근거가 다르게 말하지 않는 한 기존 제품과 화면 계약을 보존한다.

## 비교와 결정

제안, 이관, 포팅, 현재 표면을 owner와 비교한다. 화면 동작 일치는 필요한 어포던스, 레이블, 상태 전이, 빈 상태와 오류, 밀도, 권한 동작을 비교하며 백엔드 기능만으로 판정하지 않는다.

owner 근거와 사용자 승인 범위가 모두 뒷받침할 때만 차이를 구현 작업으로 표시한다. 소스 근거가 정책, 제품, 접근, 소유권을 열어두면 필요한 결정과, 확인된 경우 그 결정 주체를 밝힌다.

답을 분명하게 할 때만 다음 라벨을 쓴다.

- `Surface role`: `Owner`, `Derived/Router`, `Legacy/Compatibility`, `Stale/Superseded`, `Evidence-only`
- `Comparison`: `Matches owner`, `Owner divergence`, `Parity gap`, `Not compared`
- `Evidence state`: `Confirmed`, `Caller intent/access policy unconfirmed`, `Decision needed`, `Insufficient current evidence`, `Out of scope`

파생 표면도 owner와 일치할 수 있고, owner와의 차이도 결정을 필요로 할 수 있다. 레거시 호환 상태는 필요할 때 `Disposition:`으로 요약할 수 있다.

## 출력과 이관

실용적인 답으로 시작한다. `Recommendation`, `Evidence`, `Difference`, `Decision needed`는 답을 분명하게 할 때만 쓴다. 표면이 여러 개면 짧은 finding으로 정리한다. 근거가 부족하면 확인한 범위를 밝히고 불확실성을 명시적으로 분류한다.

사용자가 실행이나 계획으로 범위를 넓히지 않았다면 owner 근거가 뒷받침하는 권고에서 멈춘다. 인접 영역도 사용자가 구체적인 소유권 질문을 했을 때만 이 감사로 다루고, 그 밖의 후속 작업은 해당 workflow에 감사 결과를 넘긴다.
