# UI Design Rigor

## 역할

범위가 정해진 품질 개선 작업을 새로운 제품 설계로 키우지 않으면서, 기존 UI 또는 이미 방향이 정해진 UI를 더 이해하고 조작하기 쉽게 만든다.

가장 작은 적용 모드를 선택한다.

- **Review:** 파일을 수정하지 않고 검토하고 보고한다.
- **Refine:** 화면 목적, 핵심 과업과 페이지 수준 구조를 유지하며 기존 UI를 개선한다.
- **Bounded build:** 목적, 주변 구조와 시각 체계가 정해진 컴포넌트 또는 영역을 설계하거나 구현한다.

화면 목적, 핵심 과업, 페이지 수준 콘텐츠 위계나 전체 레이아웃을 결정해야 한다면 더 넓은 UI 설계가 필요하다고 보고한다.

## 권한 경계

- 사용자가 변경을 요청하지 않았다면 review를 읽기 전용으로 다룬다.
- Refine과 bounded build에서는 화면 목적, 핵심 과업, 페이지 수준 위계와 기존 디자인 시스템을 보존한다.
- 의도적인 브랜드, 도메인, 위험, 수명주기와 권한 구분을 보존한다.
- 국소 문제를 해결하려고 새 디자인 시스템, 페이지 템플릿, 내비게이션 모델이나 제품 플로우를 만들지 않는다.
- 네이티브 플랫폼 동작과 기존 컴포넌트를 우선한다. 현재 시스템이 표현할 수 없는 책임이 있을 때만 컴포넌트나 variant를 추가한다.
- 관찰한 문제와 취향을 분리하고 중요한 권고의 결과를 밝힌다.

## 관련 참조 읽기

작업에 필요한 참조만 읽는다.

- 위계, 그룹화, 일관성, 색상, 타이포그래피나 장식은 [visual-structure.md](references/visual-structure.ko.md)를 읽는다.
- 과업 완료, 피드백, 오류, 복구나 cognitive walkthrough는 [interaction-and-task-review.md](references/interaction-and-task-review.ko.md)를 읽는다.
- 폼, custom widget, 키보드, 포커스, 의미 구조, 대비, 확대나 반응형 검사는 [component-behavior.md](references/component-behavior.ko.md)를 읽는다.
- 브라우저 또는 computer-use agent가 의도된 조작자일 때만 [agent-compatible-ui.md](references/agent-compatible-ui.ko.md)를 읽는다.
- 사용자가 확률적, 생성형, 개인화 또는 자율 AI 동작과 직접 상호작용할 때만 [human-ai-interaction.md](references/human-ai-interaction.ko.md)를 읽는다.

## 작업 흐름

### 1. 범위를 고정한다

모드, 범위에 포함된 화면 또는 영역, 보존할 사용자 과업, 페이지 수준 구조, 제품 관습과 사용 가능한 근거를 정한다. Review의 읽기 전용 경계와 변경 요청의 수정 경계를 밝힌다.

### 2. 현재 시스템을 조사한다

처리 방식을 제안하기 전에 구현과 가장 가까운 제품 패턴을 조사한다.

- 같은 의미에 맞는 컴포넌트, variant, token, 언어와 상호작용 관습을 재사용한다.
- 외형과 동작을 비교하고 불일치와 의도적인 제품 구분을 나눈다.
- 정적 스크린샷만으로 런타임 동작, 반응형 품질이나 접근성 준수를 추론하지 않는다.

### 3. 핵심 과업을 추적한다

사용자 목표를 한 문장으로 쓴다. 가장 짧은 의도된 행동 순서와 비용이 큰 실패 또는 복구 경로를 추적한다. 발견, 연결, 피드백이나 복구가 불확실하면 task-review reference의 cognitive walkthrough를 사용한다.

### 4. 장식보다 구조를 먼저 검토한다

다음 순서로 확인한다.

1. 콘텐츠와 행동 우선순위
2. 그룹화와 읽기 순서
3. 외형과 동작의 일관성
4. 시스템 상태, 오류와 복구
5. 컴포넌트 의미 구조와 입력 동작
6. 제한된 너비와 긴 콘텐츠에서의 반응형 연속성
7. 타이포그래피, 색상, 효과와 장식

보편적인 스타일 체크리스트를 적용하지 말고 visual 및 component reference의 상세 규칙을 사용한다.

### 5. 관련 상태와 근거를 확인한다

범위 안의 과업에서 실제로 생길 수 있는 상태와 반응형 조건만 확인한다. 상태, 선택, 오류와 인터랙션을 색상만으로 전달하지 않고 국소 실패에서도 과업 맥락을 유지한다.

각 주장의 근거를 밝힌다.

- **Verified:** 이름을 밝힌 명령, 도구, viewport, 상태나 상호작용으로 테스트 또는 측정했다.
- **Observed:** source나 렌더 결과에서 직접 확인했지만 완전히 실행하지 않았다.
- **Inferred:** 현재 근거상 가능성이 높지만 런타임, 콘텐츠, 브라우저나 보조 기술에 의존한다.
- **Not tested:** 필요한 근거가 없거나 범위 밖이다.

대응하는 테스트 없이 WCAG 준수, 반응형 완결성, 키보드 조작이나 스크린리더 동작을 주장하지 않는다.
자동 검사는 상호작용 테스트와 사람의 판단을 보조할 뿐 대체하지 않는다.

### 6. 근거가 지지하는 범위만 바꾼다

Refine 또는 bounded build에서는 다음을 따른다.

- 미적 polish보다 영향이 큰 과업, 상태와 의미 구조 문제를 먼저 고친다.
- 일회성 값보다 호환되는 기존 token이나 컴포넌트를 우선한다.
- 그룹화, 위계, 어포던스, 상태나 브랜드 표현 역할이 있을 때만 새 시각 처리를 유지한다.
- 변경 뒤 같은 이름의 상태를 다시 확인한다.
- 인접 재설계, 컴포넌트 라이브러리 정리와 추측성 추상화를 피한다.

## 출력

Review에서는 사용자 영향 순으로 finding을 먼저 제시하고 위치, 근거, 결과와 가장 작은 적절한 권고를 포함한다. 우선순위에 도움이 될 때만 severity를 쓴다.

- **Blocker:** 과업 완료를 막거나 콘텐츠·control 손실, 심각한 접근성 장벽, 위험한 중요 행동을 만든다.
- **Major:** 위계, 상태, 복구나 예상 동작을 실질적으로 흐린다.
- **Minor:** 과업을 막지 않지만 명확성이나 polish를 개선한다.

확인한 범위와 테스트하지 않은 영역으로 review를 끝낸다. Hard failure가 평균 점수 속에서 사라지는 점수 체계를 쓰지 않는다.

변경 작업에서는 보존한 목적과 과업, 바꾼 영역, 재사용하거나 추가한 시스템 요소, 이름을 밝힌 검사와 해결되지 않은 판단 또는 위험을 보고한다. 작업 크기에 맞게 답하고 사용자의 검증에 도움이 되지 않는 내부 worksheet는 생략한다.

## 최종 확인

- 화면 목적, 핵심 과업과 페이지 수준 구조를 보존했는가?
- 사용자가 다음 행동과 현재 상태를 이해하고 관련 오류에서 복구할 수 있는가?
- 외형, 의미 구조와 동작이 같은 기대를 만드는가?
- 모든 완료·품질 주장을 근거가 지지하는가?
